## What the app does

Household stock/inventory tracker. Each item records how much is typically used per month and how much is on hand; the app computes the amount to buy to return to the ideal monthly level.

Core computation: `needToBuy = max(0, monthlyUsage - currentQty)` — e.g. 12 cartons/month used, 2 on hand → buy 10.

## Project intent

This is a **learning project focused on going deep on Kotlin Multiplatform**, not on shipping the fastest MVP. Prefer idiomatic, well-explained KMP patterns over shortcuts — especially around `expect`/`actual`, the shared-vs-platform-code boundary, and multiplatform library integration. Explaining *why* a KMP pattern is used is part of the deliverable, not overhead.

## Module layout

Generated by the JetBrains KMP wizard. Package namespace is `com.family.refillr`.

| Module | Role |
|---|---|
| `shared` | Compose UI **and** business logic for every target. `App.kt` is the shared root composable. |
| `androidApp` | Android host — `MainActivity.kt` |
| `iosApp` | Xcode project — `iOSApp.swift`, `ContentView.swift`. Built only on CI. |
| `webApp` | Web host — `main.kt`, `index.html`, `styles.css` |

`settings.gradle.kts` includes `:androidApp`, `:shared`, `:webApp`. `iosApp` is an Xcode project, not a Gradle module; it consumes `shared` as a framework.

**Note this is not the `composeApp` single-module layout** most Compose Multiplatform tutorials show. Blog posts assuming `composeApp/` will not match this tree.

`shared` source sets: `commonMain`, `androidMain`, `iosMain`, `jsMain`, `wasmJsMain`; tests in `commonTest`, `androidHostTest`, `iosTest`, `webTest`. `Platform.kt` declares `expect` in `commonMain` with an `actual` per platform — the reference example for the `expect`/`actual` pattern in this repo.

`shared` uses the **`com.android.kotlin.multiplatform.library`** plugin, not the classic `com.android.library`. Documentation about `android { }` blocks in a shared module often does not apply.

## Commands

Run from the repo root. `ANDROID_HOME` must be set (see below).

```bash
./gradlew tasks                                  # task names shift between versions; check here first
./gradlew :androidApp:installDebug               # build + install on a running emulator/device
./gradlew :shared:testAndroidHostTest            # shared unit tests on the JVM
./gradlew :webApp:wasmJsBrowserDevelopmentRun    # web dev server (first run downloads node/yarn/binaryen)
```

Single test:

```bash
./gradlew :shared:testAndroidHostTest --tests "com.family.refillr.SharedCommonTest"
```

**Always module-qualify.** Both `shared` and `webApp` register wasm tasks, so a bare task name is ambiguous.

Emulator lifecycle is scripted — see `scripts/README.md`:

```bash
./scripts/android/emulator/emulator.sh start     # or emulator.ps1 on native PowerShell
```

*Verified against this build: `tasks`, `installDebug`, `testAndroidHostTest`, `wasmJsBrowserDistribution`, `wasmJsBrowserDevelopmentRun`. Android renders the shared Compose UI on a device; web renders it at `http://localhost:8080/`.*

First Wasm build takes ~7 minutes (downloads node, yarn and binaryen); later ones are fast. The dev server blocks the terminal — it does not return.

## Environment setup

`ANDROID_HOME` must point at the Android SDK. Run `scripts/android/setup-android-home/` once per machine.

**Do not put `sdk.dir` in `local.properties`.** That file is gitignored and per-project, so it needs redoing on every clone. Worse, an *empty* `sdk.dir=` — which the wizard ships — wins AGP's precedence order and then supplies nothing, blocking the `ANDROID_HOME` fallback entirely. The line has been removed deliberately; Android Studio rewrites it with a correct value on sync, which is harmless.

Environment variables only reach processes started afterwards, so restart the terminal after first setup.

## Hard environment constraint: no Mac

Development happens on **Windows with no Mac and no local Xcode**. Never propose a workflow whose only path runs through local Xcode.

Gradle **registers** the iOS tasks on Windows (`compileKotlinIosArm64`, `linkDebugFrameworkIosArm64`, `embedAndSignAppleFrameworkForXcode`) and configuration succeeds, but they fail if invoked — Kotlin/Native Apple targets need the Xcode toolchain to link. Listing is not capability. Expect this warning on every build:

```
Native task 'iosSimulatorArm64Test' is disabled
Reason: simulator tests require macOS
```

**Consequence: `iosMain` is unverifiable locally and rots silently.** iOS CI (Codemagic or a GitHub Actions macOS runner) should land early, not last, so breakage surfaces per-commit instead of in one large batch.

The Android build must be distributable so family and friends can install it.

## Locked technical decisions

These are settled. Do not re-open or propose alternatives.

- **UI**: Compose Multiplatform — the actual UI layer is shared, not just business logic.
- **Backend/data**: Supabase via `supabase-kt`. Not a custom server, not local-only storage. Chosen for minimal server maintenance, real Postgres, built-in auth, and Row Level Security.
- **Sync**: cross-device real-time (or near-real-time) sync is a requirement. This is a shared household app.

## Web target: both `js` and `wasmJs`

The wizard configured **both**, and this is deliberate — `composeCompatibilityBrowserDistribution` combines them so browsers without Wasm GC support fall back to the JS build.

The trade-off to weigh before writing many `expect` declarations: dropping `js` shrinks the `actual` surface for every platform abstraction, at the cost of browser support.

## Target platforms

Android, iOS, Web (regular site), and Web as an installable PWA.

The wizard ships a bare `index.html` in `webApp` with **no manifest and no service worker** — PWA installability is unimplemented work, not something already provided.

## Data model

Multi-user household model — each person has their own Supabase Auth account, and a household groups them.

```sql
households (id, name)
household_members (household_id, user_id)
items (id, household_id, name, monthly_usage, current_qty, unit)
```

Items belong to a **household**, never to an individual user. Row Level Security is the access-control mechanism: a user may read/write an item only if a `household_members` row links them to that item's `household_id`. Two accounts must both see and edit the same household's data.

## Future feature to leave room for: biometric unlock

Face ID / fingerprint as a **local gate in front of an already-active Supabase session** — not a replacement for account login. Do not build it now, but do not make it hard to add. It will need an `expect`/`actual` abstraction:

- Android: `androidx.biometric.BiometricPrompt`
- iOS: `LocalAuthentication` / `LAContext`
- Web: no direct equivalent — likely skipped (WebAuthn is a different flow, not a drop-in)

Practical implication: keep session state and the "app is unlocked" gate as separable concerns from the start.
